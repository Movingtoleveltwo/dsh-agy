## 【一、底层本质（灵魂）】

**连接断了，只能证明这条连接出了问题；账号不能用了，必须拿出这个账号不能用的证据。重试属于一次请求，配额属于一个额度分组，撤销属于一份凭据，这三种权力不能混在一个“失败次数”里。**

### 1.1 总体结论

本基线属于**“局部修复已经生效，整条请求链尚未闭合”**，不能作为“四态隔离已经完成”的交付版本。

1. **不能再把基线概括为“网络错误直接当成 401”。** 普通套接字错误已经归为网络故障，普通网络故障也已经不冷却、不切号。但显式账号代理上的同类错误仍走另一条“换号”分支；刷新阶段和生成阶段对同一故障的动作不一致。
2. **最大的停号风险不只是分类词不准，而是证据被回退链覆盖。** 前一个端点的 429 可以被后一个端点的普通 403 取代，后者再被解释为凭据失效。错误的来源和作用域在进入状态机之前就丢了。
3. **当前“配额耗尽”不要求确认真实零余额。** 错误文本中出现配额词汇就可能触发长冷却；周额度剩余 1% 也可能触发顺延。它与本任务要求的“真实 0% 才接力”不是同一套规则。
4. **当前代码存在“指针已经切了，本轮请求却结束了”的断层。** 硬配额失败会先改活动账号，再抛宿主默认不重试的 `QUOTA`；凭据撤销也缺少完整的本轮接力。兼容接口另有两次尝试循环，与主插件的行为不一致。
5. **配额缺组确实能解释显示异常，但没有找到“缺值统一填 100%”的实现。** 更准确的风险是：徽标没有当前模型上下文，读第一个可用分组；Gemini 分组缺失而其他分组为满额时，用户可能把其他组的 100% 看成 Gemini 的 100%。
6. **官方产品升级可以确认，端点迁移不能冒充已经实测。** 本次公开核验确认命令行客户端 1.4.7、桌面应用更新流 2.26.0，以及 Gemini 4 Argon 已发布；但未对用户真实账号做 daily/prod 对照，不能断言“某个端点已经永久替代另一个”。

**推荐目标：以稳定单号为默认，只在具备账号级或额度级强证据时顺延；未知情况宁可有界失败，也不能靠猜测给账号判刑。**

### 1.2 四态应是四种分流结果，不是四个互斥的账号标签

四态的物理归属不同：

```text
链路故障 ➔ 本次请求的重试记录
瞬时限流 ➔ 本次请求／对应服务的短时等待记录
真实耗尽 ➔ 账号 × 模型或共享额度组 × 配额窗口的阻塞记录
验证／撤销 ➔ 账号资格或 OAuth 凭据的状态记录
```

同一账号可以同时发生“某个请求网络中断”和“另一个模型组额度为零”。把二者写进同一个账号状态枚举，后到的网络错误就可能覆盖先前的配额证据；反过来，配额冷却又可能被解释成网络等待。**隔离的核心是分开存放、分开授权写入，不是增加几个错误字符串。**

“100% 区分”也必须拆成两句话：

- **可以用类型、写入权限和测试保证：只有网络证据的事件，100% 无权切号、冷却、撤销或打验证标记。**
- **不能保证：在服务器不返回状态、字段缺失或代理中断时，100% 知道上游实际发生了什么。** 必须保留“证据不足”的出口。未知不能自动升级成耗尽，更不能升级成封禁。

## 【二、全局框架（骨架）】

**先保住“错误事实不变形”，再决定“谁有权改状态”，最后才讨论“下一次请求发给谁”。顺序倒过来，换得越快，误伤越大。**

### 2.1 当前调用链与断点

```text
主插件：src/index.ts
  ➔ createAgyRuntime
  ➔ AgyAdapter.stream / streamInner
  ➔ AgySessionManager.getSession
      ➔ pickAccount：选活动账号或顺延
      ➔ accessTokenFor / refreshToken：取得访问令牌
      ➔ loadCodeAssist：必要时补项目
  ➔ accountFetch：绑定该账号的出口
  ➔ fetchAgyFirstOk：daily → prod → daily-sandbox → autopush
  ➔ classifyHttpError / classifyFetchError：分类
  ➔ reportFailure → decideRotation：改账号状态、可能改 activeIndex
  ➔ 抛宿主错误码 → 是否再次请求由宿主重试插件决定

兼容接口：web/openai-relay.ts
  ➔ 同一个生成适配器
  ➔ 自己另做至多两次尝试，不完全采用宿主重试规则

配额展示：管理接口／会话头徽标
  ➔ refreshLimits：只测活动账号
  ➔ probeQuotaSummary → retrieveUserQuotaSummary
  ➔ cachedLimits → 卡片／徽标
                       ↘ 当前部分调度恢复逻辑也会读取它
```

这里有三条必须修补的接缝：

- **回退接缝**：多个端点的响应被压成最后一个响应，丢失前因。
- **写入接缝**：分类结果直接进入可修改账号对象的函数，网络与配额共用失败计数和存储事务入口。
- **执行接缝**：状态机“建议重试”并不等于有人真正按建议原地等待；“已切到乙”也不等于当前调用会用乙重发。

### 2.3 目标四态：动作和写权限总表

| 分流结果 | 足够的输入证据 | 本次请求动作 | 允许持久写什么 | 明确禁止 |
|---|---|---|---|---|
| 状态 1：网络抖动／本地超时 | 未取得有效上游 HTTP 响应；套接字、连接超时等传输证据；用户取消另分支 | 固定原账号与原出口，有界退避；预算耗尽返回真实网络错误 | 脱敏诊断、每次尝试的用量记录；不得通过此事件写账号惩罚状态 | 改 `activeIndex`、冷却、停运、验证标记、额度限流记录、改指纹、清掉有效凭据 |
| 状态 2：瞬时软限流 | 有效 429；短等待提示，且无同作用域硬耗尽强证据 | 原账号短时等待；遵守服务端最早重试时间 | 请求级／服务级短时节奏记录，不写账号健康惩罚 | 切号、长冷却、把失败次数变成耗尽证据 |
| 状态 3：真实配额耗尽 | 有效 429／配额型 403，加同账号、同模型或共享组、同周期的新鲜权威零余额，并能关联本次拒绝 | 原子记录阻塞，再顺延至下一可用账号；本轮可继续 | 对应额度作用域的耗尽证据、上游重置时刻、合法的活动指针变更 | 用本地累计用量推零余额；用其他模型组的零余额；借到期估计冒充官方释放时间 |
| 状态 4甲：账号验证挑战 | 受信调用上下文中的 403、明确的 `VALIDATION_REQUIRED` 等已确认结构化挑战；链接单独校验 | 标记待验证，暂避该账号，合法顺延 | 挑战原因、时间、安全展示的验证链接、下次受控复查时刻 | 当成 `invalid_grant` 永久停用；自动跟随链接、替用户完成验证 |
| 状态 4乙：凭据确已撤销 | OAuth 刷新接口明确拒绝正确绑定的客户端；本任务强证据是 400 `invalid_grant`，旧账号多候选均明确拒绝 | 禁用这份凭据，合法顺延；无其他可用账号才返回需重新登录 | 撤销状态与时间、清理对应访问令牌缓存 | 因网络、非法客户端配置、普通 403 或单个未匹配候选就撤销 |
| 辅助出口：证据不足／请求错误／取消／服务异常 | 无法满足上述强证据，或属于请求内容／调用生命周期 | 按请求语义有界重试或直接返回；取消立即停止 | 必要诊断；账号惩罚写集为空 | 为了凑齐四态，把所有未知错误塞进认证或耗尽 |

“有界重试”不等于永远重试；“不改活动指针”指**网络事件无权改它**，不是锁住全局指针、不让用户或另一条有强证据的请求合法操作。

## 【三、核心机理（血肉）】

**可靠的改造不是“更积极地换号”，而是把每次状态变化变成一条可解释、可复现、可拒绝的证据链。下面先解释现状，再给出可实施的结构与测试。**

### 3.1 端点变化：已经证实什么，仍缺什么

| Argon 提供给符合条件的付费 Pro／部分设备试用、Ultra、企业用户；不在旧 IDE 提供，而在桌面应用、命令行和 IDE 扩展提供 | [官4]、[官6] | “模型不存在”“套餐不允许”“该客户端渠道不支持”不能统一解释成账号坏了 |

官方模型页中的 `data-model-id="gemini-4-argon"` 是网页模型选择器的标识。本次没有证据证明它与 Cloud Code 生成方法的请求标识完全相同，**不能据此直接写死目录或兼容别名**。

同一网页演示了“Gemini 模型”“Claude 与 GPT 模型”的五小时和每周额度，并展示 100%。那是页面示意内容，不是线上账号测量，不能拿来证明 `grouped_summary` 的响应结构，更不能用来补缺失余额。

#### 3.1.2 对“端点漂移”的准确判断

现有证据支持下列较窄、但可执行的结论：

- 公开产品、模型和套餐能力确已继续演进；仓内历史响应的代表性必须重新检查。
- 用户提供的“daily 与 prod 返回不同分组”与当前解析、回退结构的脆弱点吻合。
- **本次没有拿到该账号在相同时间、相同出口、相同请求体下的双端点响应，因此没有证明缺组唯一由主机迁移造成。** 套餐、项目、客户端元数据、响应版本、灰度范围都可能改变结果。
- `grouped_summary` 目前只是一条待核实的字段／结构线索。本仓库既未消费它，也没有足够证据确定它位于顶层、嵌套对象还是别的方法响应。不能凭字段名猜一层兼容代码就宣称修复。

**建议把端点“顺序”提升为“按方法维护的能力策略”，但任何默认顺序调整都必须有同条件对照证据。** 配额查询可完整性补查，生成则不能因为配额查询在 prod 较完整，就直接改成 prod 优先。

### 3.2 当前实现：已修复部分与仍然可达的风险

#### 3.2.1 普通网络已隔离，显式代理还没有

直接路径如下：

```text
普通连接断开
  ➔ classifyFetchError → network-error
  ➔ decideRotation → retry
  ➔ 不设冷却、不改活动指针

相同底层错误 + 显式账号代理
  ➔ classifyFetchError → proxy-unreachable
  ➔ decideRotation → rotate
  ➔ reportFailure 写 activeIndex = 下一个账号
```

依据：`src/runtime/classify.ts:359–378`、`src/runtime/rotation.ts:331–355`、`src/session.ts:1280–1293`。

这能解释为何“直连已修好，Clash 波动仍切号”。即使不同账号拥有不同代理、换号有时能提高可用性，**那也是另一套故障转移政策，与本任务明确要求的网络原地重试相冲突**，不能偷偷保留。

另一方面，刷新阶段遇到显式代理故障，`session.ts:485–486,1073–1079` 是抛出传输错误，并没有切号。同一物理故障在两个阶段出现不同调度动作，说明修复停留在局部分支。

还有两个隐蔽耦合：

- `reportFailure` 对所有类别先增加同一个 `failureCounts`，随后无条件进入 `store.mutate`（`session.ts:1186–1209`）。普通网络虽然不改惩罚字段，仍经过账号文件写入口；真实文件存储的 `mutate` 会锁内读取并写回（`store/accounts.ts:269–275`）。写盘失败还可能盖掉原本要报告的网络错误。
- 当前软限流**已经被排除在**族限流记录和指纹重建之外（`session.ts:1218,1266`），这点应保留。但普通网络与软限流仍能抬高混合失败计数，影响之后非软限流的指纹再生门槛。身份生命周期不应由这一混合计数推动。

目标不是把 `proxy-unreachable` 名字抹掉，而是保留其诊断价值，同时剥夺它的切号权。代理故障仍必须封闭处理：不能换成直连，也不能借“重试”更换出口。

#### 3.2.2 最后一个端点的响应可能给前面的故障定罪

`fetchAgyFirstOk` 跳过 429、403、503；若没有其他状态，返回最后一个被跳过的响应。非代理网络异常继续下一端点，显式代理的特定错误则立即抛出。全链没有保留给调用者的尝试历史。

**静态可达、未做线上复现的反例：**

```text
daily：429
  ➔ prod／daily-sandbox：同样被跳过或网络失败
  ➔ autopush：403，含“无许可”而不含配额关键词
  ➔ 回退函数只返回这个 403
  ➔ classifyHttpError → auth-failure
  ➔ decideRotation → enabled = false，verificationRequired = true
```

前一站的软限流甚至验证挑战，也可能被后一站的成功或另一种错误遮掉。这里的病根不是多加几个关键词，而是**端点是否支持此账号，和账号凭据是否有效，被揉成了一个结果**。

另外，跳过的响应没有明确取消响应体；每次回退复用同一请求初始化内容。即使没有向用户输出，也不能假设上游一定没执行，或者同一个请求标识天然提供幂等保障。

目标：回退层返回带“方法、端点、阶段、状态、时间、结构化拒绝原因”的证据；处置响应体；由上层明确选择下一步。429 必须先执行限流判断，不能把换端点当成绕过等待。

#### 3.2.3 当前硬耗尽是“文字推断”，不是“余额证明”

`classifyRateLimit` 的实际规则是：

1. 命中 `quota exhausted` 等词，直接判硬耗尽；
2. 否则 `Retry-After < 3000ms` 判软限流；
3. 其他等待提示判一般限流；
4. 没有等待提示但含 `quota`／`RESOURCE_EXHAUSTED`，仍判硬耗尽。

依据：`src/runtime/classify.ts:95–120`。这意味着一句“资源耗尽”就可能带来账户级长冷却；它也可能只是共享容量紧张、请求速率限制或某端点能力限制。

后续动作进一步扩大了范围：

- `quota_exhausted` 默认五小时冷却，最高七天，写的是全账号 `coolingDownUntil`（`rotation.ts:268–290`）。
- `rate_limited` 与 `unknown` 仍返回 `rotate`；`reportFailure` 还会记入族限流。这两类没有可信零余额，也会切号（`rotation.ts:292–300`；`session.ts:1218–1224`）。
- `decideRotation` 没有模型参数；选择耗尽期限时遍历所有 `cachedLimits.groups`，可能让 Gemini 的失败继承 Claude 的周窗口（`rotation.ts:251–282`）。
- `isFamilyQuotaExhausted` 对周窗口使用 **≤1%**，而非严格零（`runtime/quota.ts:581–595`）。低余额预警和实际耗尽是两种不同事实；“1% 还能撑几小时”的注释推算也不是 Google 的计费契约。

不能漏掉已修复部分：第三、第四轮回归已对锁内选号、全池期限、部分模型族过滤、重置时刻新测仍为零等做了防护。**不能泛称所有期限路径都串组；需要修的是仍然没有模型作用域的入库与恢复路径。**

时间解析也需收紧：`classify.ts:124–141` 把较小数值当“从现在起多少秒”，若输入实际为 Unix 秒时间戳就会误算；403 配额分支还丢掉已解析的 `Retry-After` 和 `resetTime`（`194–201`）。这些字段必须按已核实的响应协议解析，不靠数值大小猜单位。

#### 3.2.4 本地用量账本无法确认剩余 0%

`stats.ts` 记录的是“本插件已经看到多少次尝试、多少输入输出用量”，按尝试累计，不是上游套餐额度总账（`stats.ts:4–37,371–387`）。它不知道：

- 官方客户端和其他进程在外部消费了多少；
- 上游按模型、工作量、套餐、窗口如何折算；
- 是否购买并允许使用超额积分；
- 网络中断但上游已执行的请求到底消耗了多少。

因此，本任务中的“账本确认”应落实为**上游权威余额观测**，而不是 `agy-stats.json`。官方允许超额积分的情况也说明：基础余额为零不必然拒绝生成，所以还需要与本次 429／配额型 403 的原因相互印证，不能用界面探测单方面提前切号。

#### 3.2.5 缺组为何会丢信息、又为何看起来像满额

当前五小时／每周链路存在三个失真点：

1. **结构失真**：`parseQuotaSummary` 只读 `groups[].buckets[]`；未知结构返回空数组，缺失／非数值比例返回 `null`，越界数值则被夹到 0～1（`quota-summary.ts:64–114`）。后者适合绘图边界，却不适合直接生成“硬零余额”证据。
2. **成功失真**：`fetchQuotaSummary` 第一个 200 就返回，哪怕解析为 `[]` 或只剩 Claude 组；不会为了补 Gemini 继续看 prod（`131–154`）。`fetchAvailableModels` 也在首个成功响应处直接类型转换返回（`models.ts:173–199`）。反而 `loadCodeAssist` 已检查是否真的提取到项目，缺项目会继续尝试，值得借鉴其完整性意识。
3. **缓存失真**：`probeQuotaSummary` 将异常归并成 `[]`；`refreshLimits` 将非空结果整份替换 `cachedLimits`。网络失败保留旧值，但“成功却少一组”会删掉旧组；一个整包 `updatedAt` 也无法表达每组分别有多新（`session.ts:555–583,642–700`）。

界面本身对未知值并没有默认 100%：`toPercent`、`windowRows` 会保留未知／过期状态。真正的范围错配在 `pickBadgeWindow` 和 `pickBadgeQuota`：它们按返回顺序取组，只收账号列表，不收当前会话模型；徽标显示通用百分数（`client/quota-view.ts:198–201,298–364`；`client/quota-badge.ts:283–315`）。

**具体推导：Gemini 正在使用 → 配额响应只有第三方组 → 第三方组为 1 → 徽标显示 100%。数字来自真实的另一个组，误导来自没有说清“谁的 100%”。** 展开卡片仍有组名，不能把这说成所有配额卡片都造假。

还有一层架构问题：`cachedLimits` 虽被注释为“只展示”，`decideRotation`、`clearExpiredState` 和阻塞期限计算实际会读取它；“没写 `cachedQuota` 就不影响调度”的注释已不可靠。

#### 3.2.6 刷新逻辑已有强防线，但需要与生成阶段统一

应保留的真实防线：`refreshAccessToken` 对已绑定客户端只用绑定值；旧账号可能尝试嵌入客户端与环境配置客户端；**全部候选明确返回 `invalid_grant` 才撤销，任何候选发生网络／未定失败就不撤销**。跨候选的最大 `Retry-After` 也保留到了后续网络失败中（`oauth/refresh.ts:103–205`；第三、第四轮回归）。有效的旧访问令牌仍可作为临时后备（`session.ts:477–479`）。

仍需处理的边界：

- `invalid_grant` 判断目前只检查错误码，不限定预期 HTTP 状态；建议将端点、阶段、客户端绑定、状态与结构一起作为撤销证据。
- 刷新 `catch` 把网络异常和成功响应的 JSON 解析失败都包为状态 0；协议漂移应该可区分，但二者都不应停号。
- `session.ts:485–486` 的显式代理分支没有把 `retryAfterMs` 继续传入 `AgyAuthError`。因此“第一候选要求等 120 秒，第二候选经显式代理网络失败”仍可能丢掉等待下限；现有第四轮测试保护的是非显式代理分支。
- 撤销写入后 `getSession` 的 `maxAttempts = 1`，取得不到令牌便抛普通错误，没有在本轮继续取乙（`session.ts:498–514,1048–1082`）。
- `probeAccount` 只刷新并调用 `userinfo`，成功后清空所有验证标记（`1462–1489`）。这可以恢复误停的 OAuth 凭据，但**不能证明 Cloud Code 的风控挑战已经解除**。两个恢复通道必须拆开。

#### 3.2.7 主插件、兼容接口、状态机三方没有同一份重试契约

`RotationAction.backoffMs` 明确只是建议；`retry`／`rotate` 没有调用者执行它（`types.ts:371–378`）。适配器将网络错误抛为 `TRANSPORT`，硬额度抛为 `QUOTA`，认证失败抛为 `INVALID_CREDENTIAL`；验证挑战暂借 `RATE_LIMIT` 让宿主重试，但不携带十五分钟账号冷却，这是已有的重要护栏。

本次实际检查安装的 `@deepseek-ai/dsh-llm@0.2.0-rc.2`，其 `lib/types/retry-policy.js` 默认白名单为：空响应、`RATE_LIMIT`、`SERVER`、`TIMEOUT`、`TRANSPORT`；**不含 `QUOTA` 和 `INVALID_CREDENTIAL`**。默认普通模式最多重试 5 次，初始等待 500 毫秒、最大等待 10 秒。执行重试的是可选宿主插件；本次未核验正在运行的桌面配置，不能保证用户一定启用了它。

| 场景 | 主插件当前表现 | 兼容接口当前表现 |
|---|---|---|
| 生成网络异常 | 抛 `TRANSPORT`，是否重试依赖宿主；重新取会话也没有显式原账号票据 | `TRANSPORT` 至少等 500 毫秒后重试，受两次尝试上限约束 |
| 软限流 | 抛 `RATE_LIMIT`，携带上游等待提示 | 至少等 1 秒，且尊重已有提示 |
| 硬配额 | 可能已切活动指针，但 `QUOTA` 在宿主默认策略下终止 | `QUOTA`／`QUOTA_EXCEEDED` 立即重试一次 |
| 401／普通认证分支 | `INVALID_CREDENTIAL` 默认终止 | 也不重试这个码 |
| 无内容时流空闲超时／上游 5xx | 适配器分别可抛 `TIMEOUT`／`SERVER`，宿主默认可重试 | `checkRelayRetry` 没有这两项 |

依据：`adapter/adapter.ts:563–569,620–676,803–811`；`web/openai-relay.ts:341–365,404,616`。兼容接口流式、非流式均最多两次尝试，最多做到本轮甲→乙，不能证明本轮甲→乙→丙。

现有 `tests/session.test.ts:1691–1760` 验证的是手动调用 `reportFailure` 后下一次 `getSession` 的圆环顺延，不是一次真实适配器调用中的完整接力。`1174` 的“撤销后本轮接力”用例仍被跳过。两者是不同验收层级。

最后，`classifyRefreshFailure` 仅由测试调用；`refreshQuotaCache`、`skipAccount` 在生产源码中只有定义，没有调用。旧排序函数的单测通过，也不能证明这些旧路径参与了当前请求。应以实际调用图而不是注释推断行为。

### 3.3 目标结构：先分证据，再分写权限

**错误处理必须先回答“发生在哪一层”，再回答“允许影响到哪一层”。输入是一条网络事实时，输出类型里就不该有修改账号的入口。**

#### 3.3.1 建议拆出的五类数据

以下字段是设计建议，不是现有接口或已确认的 Google 响应字段。

| 数据对象 | 最少需要携带什么 | 生命周期／用途 |
|---|---|---|
| 失败事实 | 请求阶段、方法、实际端点、是否收到上游响应、状态码、结构化错误、脱敏传输原因、等待提示及来源、是否已提交内容 | 每次尝试一份；只能描述事实，不直接改变账号 |
| 配额观测 | 稳定账号标识、模型或共享桶标识、窗口、原始合法比例、观测时间、响应结构版本、来源端点、重置时刻、完整性与可信等级 | 缓存与判据；失败、未知、部分成功、完整成功必须可区分 |
| 请求重试票据 | 固定账号标识、固定出口配置版本、请求截止时间、各类尝试计数、已访问账号集合、是否已提交、当前处置原因 | 只属于本次调用，不等同全局 `activeIndex` |
| 账号／额度状态 | 手动启用状态、凭据状态、验证挑战状态、按额度桶保存的阻塞证据 | 持久状态；网络与短软限流不得写入 |
| 已提交的接力事件 | 原账号、新账号、明确原因、证据引用、提交时间与状态版本 | 存储事务成功后才产生；用于诊断，不再算一次模型请求 |

关键约束：

- 网络／软限流的决策返回“同号等待”或“本次结束”，**不能返回账号状态补丁**。
- 耗尽决策必须持有通过验证的配额证据；撤销决策必须持有通过验证的 OAuth 拒绝证据。不能只接受任意字符串 `kind = auth-failure`。
- 将 `decideRotation` 从“边判断边修改账号对象”改为“纯判断，返回带权限的动作”；由单独的提交函数验证版本并应用最小补丁。
- 将混合 `failureCounts` 拆成请求级计数，例如网络尝试次数、软限流次数、协议重采样次数。它们不能累计成账号有罪的证据，更不能触发身份再生。
- 手动禁用、凭据撤销、待验证不能再只靠同一组布尔值互相覆盖。兼容旧字段可以，但内部含义必须独立。

#### 3.3.2 统一判断顺序

```text
收到失败
  ➔ 用户明确取消？是：立即结束，无重试、无账号惩罚
  ➔ 没有有效上游 HTTP 响应？是：传输／本地协议分支
       ➔ 确认可重试的链路问题：状态 1，同账号、同出口
       ➔ 证书配置等确定性错误：有界失败，不改账号
  ➔ OAuth 刷新阶段？
       ➔ 正确客户端的全部必要候选明确 invalid_grant：状态 4乙
       ➔ 429／服务错误／不确定结果：请求级等待或失败，不推断模型耗尽
  ➔ Cloud Code 明确验证挑战？是：状态 4甲
  ➔ 配额型拒绝 + 同作用域的新鲜零余额强证据？是：状态 3
  ➔ 短时 429、没有硬耗尽强证据？是：状态 2
  ➔ 其余：证据不足、请求错误或服务异常；不获得账号惩罚权
```

特殊规则：

- **普通 401 不等于刷新凭据撤销。** 可对原账号做至多一次受控刷新并重发；若刷新成功仍被某端点拒绝，应报告该端点／许可问题，不循环停用账号。只有确认 `invalid_grant` 等撤销证据才走永久禁用。
- **普通 403 不等于凭据撤销。** 无许可、区域不可用、模型不在套餐内、某端点拒绝，都是更窄的能力问题。没有独立强证据时不切号、不撤销。
- 验证挑战优先识别已确认的结构化错误。合法挑战即使没有可用链接，也不变成认证失败；界面明确“待验证，链接未提供”。散文里偶然出现 `verify` 不能产生挑战状态。
- 429 的短等待只是软限流线索，不是数学证明；若同一请求另有可信硬零余额，按状态 3。若两个来源冲突，则先保留冲突并受控复查，不能悄悄选“最严重”的那个。
- 长 `Retry-After`、重复 N 次 429、没有 `Retry-After`、包含 `RESOURCE_EXHAUSTED`，都**不能单独升级为硬耗尽**。可原账号有界等待，也可因超过交互预算而返回，不能因此切号。
- 代理预检自行生成的 503、代理认证拒绝等，要标注为本地／代理层；不能按 Google 的有效 503／403 去处罚账号。

#### 3.3.3 硬耗尽证据的七道门

一个观测只有同时满足下列条件，才能赋予状态 3 的写权限：

1. **账号一致**：绑定稳定账号标识，不靠当前数组下标。不能把活动账号切换前的响应写到切换后的账号。
2. **能力一致**：对应本次请求模型，或已验证该模型确实共享的额度桶。Claude 与 GPT 的第三方共享桶可按已确认映射共享，但不能影响 Gemini。
3. **窗口一致**：五小时、每周、其他已确认窗口分别保存；每模型 `quotaInfo` 不带窗口时，不能自行命名为五小时或每周。无法建立映射就不能拿来判本次硬耗尽。
4. **数值确实为零**：原始值必须是合法、有限、在协议范围内的数字 0。`null`、缺值、字符串、负数夹成 0、四舍五入显示为 0%、周剩余 1%，均不满足。
5. **足够新且处于同一周期**：缓存年龄、窗口重置边界、账号／项目配置版本必须一致。可复用满足严格新鲜度的观测，否则失败后只做一次合并的受控探测；不是每次重试都查一遍。
6. **来源与完整性可信**：已识别响应结构、目标桶未丢失、没有与新观测冲突。某个桶的明确零值可以证明该桶阻塞，不要求另一无关桶也为零；但要证明“账号对该模型已经恢复”，必须覆盖所有已知阻塞桶。
7. **拒绝原因相符**：本次 429／403 与该额度拒绝相关，不是容量、权限或代理错误；基础额度零但超额积分仍可用的成功请求，不触发提前停用。

建议将“可处罚观测”的新鲜度设得明显严于展示缓存；例如先以**不超过 30 秒**作为待验证的工程起点，结合重置边界立即失效。这个数字不是 Google 的保证，也不是本次测出的阈值，必须经延迟与一致性测量后调整。已有较久的零值可作为旧阻塞的历史依据，但不能伪装成刚刚取得的新证据。

探测失败时，结论是“暂时无法确认”，不是“默认耗尽”或“默认满额”。不能为了提高自动接力成功率而放宽这七道门。

### 3.4 一个重试执行者：请求必须真正原地等待、真正接力

**状态机决定“可以做什么”，执行器负责“什么时候、对哪个账号做”。两者分开，但同一层只能有一个真正发起重试的执行器。**

#### 3.4.1 推荐方案与替代方案

推荐在插件共享运行时建立统一请求编排器，主插件和兼容接口都使用它：

- 同号网络重试、软限流等待、合法跨号接力，由同一个编排器消费决策。
- `AgyAdapter.streamInner` 负责一次上游尝试的构造、解析与提交边界，不再一边修改池、一边指望外部恰好重试。
- `AgySessionManager` 提供“解析指定稳定账号”“提交已验证状态转移”“顺延选择”的能力，不自己再隐藏另一套循环。
- 兼容接口只转换输入输出和最终错误，不再对编排器已经耗尽预算的失败额外重试。
- 对 agy 路由，宿主重复重试必须关闭或能识别“本次重试预算已经消费完”的契约；不能让插件内重试与默认宿主五次重试相乘。

当前 `src/index.ts:16–24` 只有适配器注册，未显式控制重试配置。**宿主关闭／委托重试的真实接口必须在实施前核实并做兼容测试，不能仅凭本报告发明一个配置项。** 不改 `node_modules`，不把账号五小时冷却伪装成 `providerRetryAfterMs` 来阻止外层重试。

替代方案是继续由宿主承担唯一执行者，但必须扩展契约，能传递原账号票据、接力授权、剩余预算和提交状态，并让兼容接口执行完全相同的规则。它对宿主改动更多，也依赖可选重试插件；仅靠现有错误码无法满足要求。

这是产品契约调整，不是一个局部 `while` 修补。仓内“适配器不隐式重试”的既有约束，需要在未来实施提交中同步明确新边界；本次不修改该约束。

#### 3.4.2 有界退避与预算

建议先采用可配置、可注入测试时钟的预算模型，而不是再增加账号失败阈值：

| 预算 | 建议规则 | 原因 |
|---|---|---|
| 单次逻辑调用总预算 | 一个共享截止时刻，覆盖刷新、配额确认、端点尝试和等待；生成内容已提交后的流生命周期另受空闲看门狗保护 | 当前多个“超时”实际各自重新计时，无法约束整体 |
| 网络重试 | 工程起点可为额外 3 次，约 0.5／1／2 秒退避并带有限抖动；固定账号、出口，优先原端点 | 克服短抖动而不横跳，不是承诺所有弱网都能恢复 |
| 软限流 | 至少等到可信的上游最早重试时刻；没有可信提示时采用有界本地退避 | 不得因为“提示太长”就缩短服务端要求 |
| 合法接力 | 一次调用中，每个可用账号至多进入一轮；账号集合去重，池内全部尝试后结束 | 防止甲→乙→丙→甲在一个调用里无穷打转 |
| 端点尝试 | 按方法的有限能力策略；与总预算合并，不再无限叠加 | 4 个端点 × 刷新候选 × 外层重试，很容易放大请求 |
| 协议重采样 | 保留现有畸形工具调用的独立上限，但必须计入同一个总预算和用量记录 | 不能再额外乘出一层无界请求 |

上述重试次数与毫秒值是设计起点，不是上游协议事实。若服务端要求等 120 秒、调用只剩 20 秒预算，应返回带真实等待信息的错误，**不能等 20 秒就重发，更不能借切号消除这个约束**。额度冷却只限制对应账号／额度桶；合法切到另一个账号，不应继承旧账号五小时的等待。

等待时间分两类保存：

- **本地退避**：调度器选择的防抖时间；只能控制本次重试。
- **上游最早重试时刻**：从真实响应解析；不能用本地策略时间冒充。

`parseRetryAfter` 允许 0，而已安装的 `LlmError` 要求 `providerRetryAfterMs` 为正有限数。因此内部可以表示“立即可试”，向宿主输出时须省略 0 或按契约正确转换，不能直接构造非法错误对象。数值秒、HTTP 日期、过去日期、无效值都要单测。

当前 `proxy.ts:457–462` 的 `withTotalTimeout` 每次调用才创建超时信号；`session.ts:565–568` 的配额超时同样按每次请求重建。四站串行时，名义每次 3 秒并不等于整条链 3 秒，刷新还另算。改造应在外层先建立截止时间，再把剩余预算和取消信号一路传下去。

#### 3.4.3 “原地”的严格含义

- 固定的是**本次重试票据中的账号和出口**，不是每次醒来重新读取 `activeIndex` 再选一个。
- 不得因为显式代理坏了而走环境代理或直连。HTTP、SOCKS、环境代理的诊断可以不同，账号处罚权限必须相同。
- 网络抖动默认先重试相同端点；确需同账号能力回退，也必须显式记为端点操作、保持出口不变，并有次数和总预算约束。
- 若用户在等待期间删号、改代理、禁用或手动切换，应检测配置／状态版本变化，取消旧票据或走明确的重新规划流程，不能静默借这次网络错误切到别的账号。
- 多请求共享短时节奏控制和刷新中的同一个结果，防止同一账号瞬间并发重发；这类内存等待不应进入账号“冷却／停运”字段。
- 管理界面的“测试此账号”是固定目标诊断，**不允许跨号接力**。乙返回成功不能被报告成甲通过测试；`testCall` 的 `accountIndex` 必须端到端保持约束。

### 3.5 端点与配额：不再让“成功的空结果”通过验收

#### 3.5.1 按方法管理回退与完整性

建议将“端点列表”与“某方法的响应验收条件”分开：

| 方法类型 | 什么才算有用成功 | 失败时的合法下一步 |
|---|---|---|
| 项目引导 | 提取出合法项目／套餐，或明确结构化表示尚未开通 | 网络／协议失败保留未定；只有明确未开通才进入开通流程 |
| 模型发现 | 结构合法，声明可用的模型和能力字段相互一致 | 缺字段标记部分成功，受控补查；保留旧目录但标明来源与年龄 |
| 配额汇总 | 返回目标模型对应桶，窗口与数值有效 | 200 缺目标组不是完整成功；允许同账号同出口下对下一授权端点做有限补查 |
| 生成 | 对应方法取得有效响应且完整解析结束 | 先分类；429／挑战不能被后站结果覆盖，网络重试与端点能力回退分开 |

所有方法都应保留端点来源。下一站无许可，最多证明下一站不可用；不能擦掉上一站的限流证据。已确定的账号级挑战／撤销也不能通过试其他端点绕过去。

不建议把不同端点“谁更大就信谁”。两个来源对同一桶、同一周期矛盾时，应保留冲突并复查；不能跨时间拼一个看似完整的最新快照。遇到大响应或异常页面只保留有界、脱敏摘要，取消不用的响应体。

#### 3.5.2 展示缓存与调度证据分开

建议引入四种配额查询结果：**失败、未知结构、部分成功、完整成功**，替代 `QuotaGroup[]` 同时表示一切。

具体规则：

1. 每个账号、每个分组、每个窗口保存自己的观测时间与来源；保留旧组时不能一起刷新旧组的时间。
2. 响应没有 Gemini 组时，Gemini 显示“未取得／旧值已过期”，不能删掉信息后让第三方组冒名顶替。
3. 若确有 `grouped_summary` 新结构，先捕获脱敏样例，再增加显式结构解析器和版本测试；旧结构继续识别。未知结构记录诊断，不递归乱找任何叫 `remainingFraction` 的字段。
4. 调度只读取“满足证据门槛”的独立观测或已授权阻塞，不读取展示百分比。这样 `refreshLimits` 可以安全更新界面，而不会间接停号。
5. 徽标优先由宿主提供当前模型上下文，匹配后台已经确认的共享桶。拿不到上下文时，显示带组名的多个值或未知，**不能默认第一组代表本轮模型**。
6. 保持徽标默认关闭、挂载／唤醒触发探测、倒计时只用缓存计算的既有界面约束；不能为补缺组新增定时网络轮询。
7. 不要求所有套餐都必须同时拥有五小时和每周桶。现有恢复代码对每个组强制要求两个窗口（`rotation.ts:174–180`），应改为以该套餐／桶已确认的阻塞集合为准；不能因免费套餐只有周额度而永久无法恢复。

#### 3.5.3 新模型与版本治理必须独立

`catalog.ts` 当前未固定 Argon；动态发现可让未知标识进入列表，但 `catalogModel` 和 `isLevelThinkingModel` 对未知模型仅有有限回退，不能因此保证档位、模态和输出长度正确。新模型应按“真实发现 → 合法调用参数 → 最小生成 → 回放工具／多模态边界”的顺序验收，不能为了显示模型名而假定支持所有旧参数。

更新版本也不能修复一切：正常入口 `resolveObservedAgyVersion` 只读命令行发布流，这是正确方向。另有一个静态风险：通用 `resolveObservedVersion` 会发布版本，IDE 解析器也调用它，而 `peekCachedAntigravityVersion` 会检查两套缓存（`runtime/version.ts:108–152,174–220`）。**正常启动不是 IDE 路径；但若同进程调用 IDE 诊断，存在把 2.x 发布进命令行全局缓存的可能。** 建议将“观察其他产品版本”和“发布用于请求的版本”完全分开。

离线回退值与指纹版本池需要按新鲜度门槛单独更新，但本次没有执行新鲜度验证脚本，不把静态比较表述为脚本实测失败。尤其不能把 Hub 2.26.0 当成命令行 1.4.7 的替代值。

### 3.6 接力与恢复：事务必须同时管住时间和身份

**顺延不是“下标加一”，而是在最新状态里找下一个确实可用的账号，并让记录、指针与事件描述同一次已经提交的变化。**

#### 3.6.1 保留现有并发修复，再补状态版本

应保留的正确结构：

- `pickNextSequentialAccount` 按圆环顺序跳过禁用、冷却、族限流和耗尽账号（`session.ts:786–811`）。
- `pickAccount` 在锁内重读最新账号数组、活动指针和时钟；事务失败不使用未提交候选；成功后才发事件（`870–925`）。
- `reportFailure` 只在失败账号仍是活动账号时改指针，迟到的甲失败不会把已选好的乙再次覆盖（`1233–1241,1284–1290`）。

目标补强：

1. 以稳定账号标识和状态版本提交，不以请求开始时的数组下标提交；删除、重排后重新定位。
2. 耗尽事件只更新对应桶，撤销事件只更新对应凭据；写集不包含无关模型组或其他账号。
3. 并发相同证据去重；同一状态转移只发一次接力事件。若另一请求已合法切到乙，本请求接入乙或明确结束，不再把指针写回甲。
4. 网络事件不进入这套可修改账号的事务接口，更不能在并发完成后“恢复原 activeIndex”来假装满足不切号。
5. 事务失败时不发成功接力事件、不使用未提交的新账号，并保留原始故障与本地持久化失败两个事实。
6. 事件原因不得写死。当前 `pickAccount` 在成功转移后固定发 `rate-limit`／`quota-exhausted`（`session.ts:913–925`），不够表达撤销、验证或管理员状态变化；目标应带原／新账号和真实证据类别。

#### 3.6.2 冷却释放时间如何才算真实

至少分开保存：

- **上游重置时刻**：真实响应给出的绝对时刻，连同桶和观测周期保存。
- **本地下次复查时刻**：上游没给时间或证据有冲突时，系统选择何时再确认；这不是恢复承诺。
- **账号资格复查时刻**：验证挑战的受控再试时刻，不是配额重置时刻。

计算规则：

```text
一个账号、本次模型有多个仍阻塞的额度桶
  ➔ 必须等所有相关阻塞解除：取相关释放时刻的最大值

多个账号中，只需任意一个可用
  ➔ 取各账号可用时刻的最小值

其中有未知释放时刻
  ➔ 明示未知与下次复查，不伪造精确的池恢复时间
```

不要把极远的上游时刻强行截到七天，然后声称七天后一定可用；可以给本地复查设置上限，但上游原始证据与本地调度上限分开。数字时间戳单位必须来自方法协议，不能靠 `> 1e12` 猜。

到点之后也不自动产生 100%：旧周期观测到期只能失效，转为“允许受控确认”；若在重置时刻之后取得的新观测仍为零，就继续保留相关阻塞。明确恢复必须来自对应能力的正向证据，并防止旧成功响应清掉后来产生的新耗尽状态。

#### 3.6.3 甲→乙→丙→甲的准确语义

- 正常情况下持续使用甲，不按低水位、并发数量或余额排名主动漂移。
- 甲满足状态 3 或状态 4，才顺延到乙；乙仍受限则顺延到丙。
- 甲恢复后，**不抢回正在健康服务的乙或丙**；只有下一次需要接力时，圆环才再次考虑甲。
- 甲仍未恢复时，不能为了凑出圆环顺序强行回到甲。
- 全池均有可信硬阻塞时，返回配额不可用及可确定的最早恢复时刻；全池凭据均撤销时才返回需要重新登录；网络失败不能降级成“没有账号”。
- 一次调用内的访问集合必须有界。跨多个调用的圆环接力和一次调用中无限循环是两回事。

#### 3.6.4 验证挑战和撤销的恢复通道

- 凭据撤销：用户重新授权，或明确验证成功恢复错误的认证停用；保留现有可恢复误判的产品承诺，但按稳定标识提交。
- Cloud Code 挑战：保存待验证原因；到达本地复查时间后，只允许受控探测，不能仅因 `userinfo` 成功而清除。需要同一 Cloud Code 能力的正向结果或明确的挑战解除证据。
- 挑战链接仅安全展示，不自动访问；限可信协议／来源，避免任意 URL 被界面当成授权验证入口。错误文本、链接进入回调页面和脚本时继续遵守既有转义规则。
- 配额恢复：只释放相关桶，不顺手清除认证／验证标记。

### 3.7 流式边界：稳定性不能靠重复执行换来

**能重试的边界不是“我还没看到最终答案”，而是“尚未向下游提交任何会被消费的内容或工具动作”。已经交出去的东西收不回来。**

应保留的基线行为：

- 流已向消费者交付内容后，断流、空闲超时均终止为上游错误，不自动重放。
- 尚未提交内容的空闲超时可报 `TIMEOUT`；当前普通中途断流或缺少结束标志的 EOF 仍是终止性 `UPSTREAM`，不能泛称所有无输出流错误都已可重试。
- `MALFORMED_FUNCTION_CALL` 最多重采样 3 次，等待 200／400／600 毫秒；思考片段、工具调用和签名缓冲到提交点，丢弃尝试不能污染全局签名缓存。
- 每次尝试已经报告的令牌用量都要入账，包括最后丢弃的尝试；接力只记池事件，不重复算一条模型请求。

锚点：`adapter/adapter.ts:599–663,789–875`、`adapter/parse.ts`；`tests/adapter.test.ts:2130–2669`。

需要补的边界：

- 发请求、取响应头之前用户取消，当前 `classifyFetchError` 会把 `AbortError` 归到网络错误，而 `sendAttempt` 再抛 `TRANSPORT`；要在最外层先检查调用者取消，不能因此进入重试。
- 统一记录“是否提交”。如果未来提前输出思考或工具动作，那么这些输出也算提交，不能仅看是否发过 `text-delta`。
- 刷新／配额／等待必须接收同一取消信号。刷新共享中的一个等待者取消，不得误中止其他等待者仍需要的刷新；所有等待者取消或共享任务达到自身预算才清理它。
- 已放弃的响应体必须取消，重试票据、定时器、并发计数必须在所有退出路径释放。
- “未收到 HTTP 响应”不证明请求没到服务器，“尚未提交内容”也不证明没消耗配额。网络重试只能提供有界恢复，**不能承诺上游恰好执行一次**。

### 3.9 分阶段实施，避免把端点换址与状态机重写绑死

| 阶段 | 交付内容 | 放行条件 |
|---|---|---|
| 第一步：冻结新契约 | 四态与未知出口、固定账号诊断模式、写权限表、旧测试去留表；保留当前测试基线 | 先写能让代理误切、未知 429 切号、普通 403 撤销暴露的测试 |
| 第二步：收回误处罚权 | 统一普通／代理网络动作；纯分类与状态提交分离；取消先行；保留失败来源 | 所有状态 1／2 测试账号写集为空；强证据不足一律不能停号 |
| 第三步：接入可信配额 | 分级响应、逐桶来源与时间、严格零判定、正确复查时间；完成受控端点对照后才选策略 | 缺组、未知、串组、旧值、舍入零全部不能制造硬耗尽 |

拆分提交有利于回退，但某阶段没完成时，不能对外宣称“四态隔离已上线”。尤其不能先删掉误切号，再保留无人执行的 `retry` 建议，导致用户看到每次网络抖动都立刻失败。

## 【四、死穴与边界（红线）】

**这套设计能严格防止“证据不够却处罚账号”，但不能制造 Google 没提供的余额、恢复时间或执行回执。遇到未知先保真，比凭空给出一个漂亮的 100% 更重要。**

### 4.1 不可跨越的边界

1. **不把超时翻译成认证失败。** 错误消息出现数字或敏感词，不等于真的收到了对应 HTTP 响应；状态 1／2 的账号写权限必须为空。
2. **不把端点拒绝放大成整个账号撤销。** 无许可、地区限制、模型不可用和客户端配置错误需要各自诊断；换端点不能覆盖明确挑战，更不能被用于绕过限制。
3. **不把未知余额改成零或满额。** 不从本地令牌账本反推上游配额，不从其他组借百分比，不从舍入结果生成处罚。
4. **不把估计时间伪装成上游承诺。** 本地复查与真实重置分开；到点只代表可以确认，不代表必然恢复，更不代表额度满了。
5. **不承诺任意弱网下都成功，也不承诺上游只执行一次。** 原地重试有总预算；请求在断线前可能已经被执行或计费。
6. **不在已经提交内容或工具动作后自动重放。** 思考、签名、用量和工具调用的现有提交语义不能因“提高接力成功率”被破坏。
7. **不把代理故障转成直连，不借诊断泄漏凭据。** 所有账号相关请求继续走绑定出口；原始刷新令牌不能出现在请求标识、遥测、测试样例、报告、截图或日志中。
8. **不自动访问验证链接、开通超额付费或扩大账号探测范围。** 接力只在用户合法持有并获准使用的账号之间进行；验证和许可限制不是“换个号就忽略”的分类分支。
9. **不借本次评估顺手改业务。** 本报告只是设计与证据；所有后续代码、存储迁移、端点试验均需独立实施。此次没有执行真实账号验证脚本、没有修改账号状态。

### 4.2 必须承认的取舍

- **更严格的证据门槛会暂时降低自动接力率。** 在 Google 缺字段或新结构尚未适配时，本次请求可能返回“无法确认配额”，而不是自动换号。这是防误停号的代价，符合本任务优先级。
- **同号重试可能错过另一个代理确实可用的机会。** 不同账号不同出口时，网络故障转移有可用性价值；但它与当前“网络绝不切号”要求相反。若将来需要，只能作为另一个明确启用的策略，不能混回默认行为。
- **统一执行器涉及宿主契约，不能只改插件半边。** 未明确外层是否还会重试前，扩大内部循环会成倍增加请求。暂时维持旧执行者也可以，但应诚实标注尚未完成同次接力。
- **旧账号状态缺少证据来源。** 不能把旧 `cachedLimits` 补上一个“当前时间”就升级成可信新观测；旧冷却要保留历史原因并受控复查。也不能批量把所有停用账号改回健康。对历史误停用，应按凭据恢复／挑战恢复的不同证据处理。
- **恢复比判某个桶耗尽需要更多覆盖。** 一个相关桶明确为零足以阻塞；要宣布完全恢复，必须逐一解除此前相关阻塞。缺少一个桶，不等于那个桶健康；无关组缺失也不应阻止当前模型恢复。

### 4.3 仍需进行、但本次没有执行的同条件实测

建议在获得真实账号探测授权后，单独编写 `scripts/verify-endpoint-matrix.mts` 一类开发验证工具，而不是把实时网络加入 `tests/`。

| 实测问题 | 最小对照方法 | 记录与放行标准 |
|---|---|---|
| 配额是否真的迁移或换结构 | 同一账号、项目、出口、客户端元数据，在相近时刻分别读取 daily／prod 的项目引导、模型发现和配额汇总 | 状态、字段结构、分组／桶／窗口、合法比例与重置时间均逐方法记录；发现 `grouped_summary` 时保留脱敏结构，不猜层级 |
| 是端点差异还是套餐／灰度差异 | 先控制同账号变量，再用少量不同合法套餐账号交叉验证，不同时改变版本与出口 | 不把单个套餐样本推广到所有账号；明确哪些桶本来就不存在 |
| 生成与查询是否应采用不同策略 | 查询完成后，对确有权限的模型做极小、限次生成；每次有独立标识与关联记录 | 配额方法成功不能替代生成方法成功；遇到验证／许可拒绝停止相应探测，不反复试图绕过去 |
| 哪个字段能证明真实耗尽 | 对已经自然发生的 429／403，关联同周期余额、结构化原因与后续恢复 | 不为了制造样例主动烧空配额；确认容量限流、速率限制和额度拒绝的区别 |
| 如何解释时间 | 比较响应时间、HTTP 日期、`Retry-After`、重置字段和实际恢复 | 先确定单位与作用域，再写解析器；缺时间保持未知 |
| Argon 在此渠道的真实能力 | 以授权账号真实发现为起点，核对请求标识、套餐许可、思考档位、最小生成，再测工具／模态边界 | 不能用官网网页标识或公开 Gemini API 的参数上限替代本渠道证据 |
| 新版本到底影响什么 | 在同条件下仅改变已确认合法的客户端元数据字段，比较方法响应；命令行版本与 Hub 版本不混填 | 若无法证明版本影响，不把端点差异归咎于版本；不扩大指纹伪造字段 |

验证输出只保留状态、方法、主机、时间、字段名和脱敏样例标识。禁止输出 `Authorization`、OAuth 密钥、访问／刷新令牌、完整代理地址及真实项目标识；不要把原始响应随手上传到公共议题。

现有 `verify:version-freshness`、`verify:official-identity`、`verify:dsh-llm-compat` 可以在各自授权范围内作为补充，但它们不能替代上述账号／方法对照。尤其 `dsh-agy verify` 只验证刷新与用户资料，不能证明配额接口、客户端元数据或生成模型可用。

### 4.4 后续实现的最终验收门槛

只有同时满足以下条件，才可宣称本任务的架构目标达成：

- [ ] 任意受测传输错误、任意路由、任意请求阶段，都只在原账号和原出口有界重试；本事件对活动指针、冷却、停用、验证和指纹的写入均为零。
- [ ] 短软限流真正等待、不切号；未知／长 429 不凭次数或关键词升级为耗尽；服务端等待下限完整保留。
- [ ] 只有同作用域的可信硬零余额与本次额度拒绝关联后才能接力；真实重置与本地复查清楚区分。
- [ ] 明确挑战、明确撤销各走独立状态与恢复路径；普通 401／403／客户端配置错误不能误停整个账号池。
- [ ] 主插件与兼容接口均通过同一次调用甲→乙→丙成功，以及跨调用甲→乙→丙→甲的测试；没有外层重试倍增。
- [ ] 同一个模型缺组、分组乱序、旧值或未知结构时，界面不显示冒名顶替的满额；展示缓存不直接产生处罚。
- [ ] 并发重读、迟到事件、状态提交失败、账号删除重排均不造成错误切号；已提交内容不重放，用量和签名守恒。
- [ ] 所有网络均被测试桩拦截；有效新契约没有靠跳过维持绿灯；另行完成经授权的端点／模型实测后才调整默认路由和模型能力。

**本次交付的是上述门槛的证据与实施蓝图，不是勾选后的完成声明。** 当前基线的绿灯是可靠起点，但还不是四态隔离的充分证据。
